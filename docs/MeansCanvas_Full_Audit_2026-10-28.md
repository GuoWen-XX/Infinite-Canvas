## 3. 已确认的工程、发布与安装问题

优先级定义：**P1** 为下一次发布前优先修复；**P2** 为近期迭代修复；**P3** 为维护改进。优先级不等于漏洞评分。证据分为“已复现”“源码确认”和“待测建议”，不将推测写成已经发生的故障。

### E01 · P1 · 测试依赖作者本机的私有画布，干净检出必然失败

- **位置**：`tests/test_runtime_issues_fix.py:92`；`.gitignore:4`。
- **证据**：测试直接读取 `data/canvases/0ce47899ea4741e49140420c4e1f526a.json`，但 `data/` 不入库。隔离副本实际产生 `FileNotFoundError`，测试退出码为 1。
- **影响**：新开发者、CI、发布验证无法稳定复现“全绿”；也将个人画布内容混入测试前提。
- **最小修改**：测试自行创建临时画布或通过隔离后的创建接口生成样本，再校验保存和重载后的 viewport；保留真实行为断言，不把该测试简单改成 skip。
- **验收**：没有 `data/`、没有 `.env` 的全新检出可运行全部确定性测试；测试结束后不留下固定 UUID 的数据文件。

### E02 · P1 · 运行依赖遗漏 WebSocket 后端，实时连接在基础安装中不可用

- **位置**：`requirements.txt:3`；`mac-安装依赖.sh:27`；`安装依赖.bat:70`；`tests/test_smoke_suite.py:222`。
- **证据**：清单只安装 `uvicorn==0.46.0`，没有 `websockets` 或 `wsproto`。已核对本机包依赖元数据，WebSocket 依赖属于 Uvicorn 的可选 `standard` extra。当前 Python 环境两个后端均缺失；实际请求 `/ws/stats` 的 Upgrade 握手返回 `HTTP/1.1 404 Not Found`，服务输出：

  ```text
  Unsupported upgrade request.
  No supported WebSocket library detected.
  ```

- **影响**：画布更新广播、在线人数、插件或实时消息链路不能按设计工作。Windows 安装器另行联网补装 extra，macOS 和纯 requirements 安装没有同样保障；离线轮子下载清单也不完整。
- **最小修改**：把一个明确支持的 WebSocket 后端纳入统一、锁定的运行依赖和离线下载流程。若只需要 WebSocket，可显式增加该依赖，避免无理由引入整组 extras；各平台均从同一清单安装。
- **验收**：全新环境仅执行清单安装后，真实 Uvicorn 进程握手返回 101，能收发 ping/pong；离线安装也通过。该用例不得因缺依赖而跳过。

### E03 · P1 · SSRF 门禁存在变量命名与控制流漏检

- **位置**：`scripts/check_ssrf_guards.py:137`、`:144`、`:146`、`:268`、`:318`。
- **证据**：扫描器在检查已识别 HTTP 客户端之前，按 `_cache` 等后缀和全大写名称排除对象；已校验变量重新赋值时又未清除原有“安全”状态。分支内调用校验也会影响分支外判断。
- **实际对抗结果**：未校验的 `client.get(payload.url)` 被捕获，退出码 1；只将客户端改名为 `gateway_cache` 或 `REMOTE`，完整门禁都变成退出码 0。另两项 AST 用例——先校验再覆盖 URL、只在一个分支校验——均未报错。删除临时文件后门禁恢复退出码 0。
- **影响**：门禁不能支撑“所有用户可控出站请求均已校验”的结论。这里确认的是门禁漏检，**不据此断言某条现有生产接口已经可利用**。
- **最小修改**：已识别的 HTTP 客户端优先于名称排除规则；重新赋值撤销旧的已校验状态；只接受在所有可达路径上先于请求发生的校验。若不实现完整控制流，保守报错并用窄范围显式例外处理。
- **验收**：两个非约定客户端名、赋值覆盖、条件分支、别名和关键字 URL 用例均能捕获；正常字典 `.get()` 不误报。遵照 AGENTS.md 保留“植入—非零—还原为零”的实际输出。

### E04 · P2 · 关键安全回归依赖真实 Key，在线 smoke 又依赖固定端口

- **位置**：`tests/test_key_exfiltration.py:52`；`tests/test_smoke_suite.py:13`、`:25`；`tests/test_smoke_adversarial.py:9`、`:20`；`.github/workflows/ci.yml:83`。
- **证据**：6 个 Key 防外泄用例在没有真实 ModelScope Key 时全部跳过；两个 smoke 类在 3000 端口未运行服务时整体跳过，而 CI 没有启动这个服务的步骤。部分测试通过完整应用直接操作默认存储目录。
- **影响**：开发者的环境配置决定测试是否执行；在真实服务正在运行时，测试还可能创建、更新或删除真实工作目录中的测试记录。CI 的通过率掩盖了未执行的链路。
- **最小修改**：统一提供临时数据目录、临时配置文件、虚构凭证和受控 DNS/HTTP 替身；smoke 由测试夹具启动临时端口的服务并明确等待就绪。安全单测不需要真实 Key，也不能发送 Key 到公网。
- **验收**：无密钥、无既有服务时所有关键安全测试都执行；一条命令完成服务启动、真实 HTTP/WS 检查和清理；CI 对关键测试的 skip 数设为零。

### E05 · P2 · 国际化门禁无法发现缺失或空白翻译

- **位置**：`static/js/i18n/validate-i18n.js:42`、`:49`；`static/js/i18n-core.js:10`。
- **证据**：校验器先构造总是具有 `zh`、`en` 属性的对象，再用属性存在性判断缺失；运行时词条归一化还会提前用另一种语言填补缺失项。追加只有中文的词条、追加英文为空字符串的词条，两次都输出 `i18n ok: 1343 keys` 并以 0 退出；恢复后为 1342 keys。
- **影响**：新增界面可在英文模式回退中文而仍被 CI 标为通过。
- **最小修改**：对原始词条验证两种语言均为非空字符串，或在注册词库时保留缺失信息供验证读取；运行时 fallback 继续保留。不要用“包含常见汉字”之类宽泛规则替代缺失检查。
- **验收**：缺中文、缺英文、空字符串及纯空格全部失败；合法完整词条通过；保留现有未解析 key 检查。

### E06 · P1 · macOS 启动器会强制结束不属于本项目的进程

- **位置**：`mac-启动服务.command:25`、`:28`、`:32`。
- **证据级别**：源码确认；未在 macOS 上执行杀进程操作。
- **触发与影响**：只要 3333 端口被其他程序占用，就先 `kill`，一秒后仍被占用再 `kill -9`；没有核对可执行文件、工作目录或本应用 PID。`lsof -ti :3333` 也未限定 LISTEN，存在误伤关联连接进程的风险。其他服务或未保存工作可能中断。
- **最小修改**：默认报告端口冲突并退出或让用户选择其他端口；如支持重启，只操作经过 PID 和进程身份核验的本应用实例，给予正常退出时间。
- **验收**：用无关测试服务占用 3333，启动画布后原服务存活，画布给出准确提示；对确认为本应用的旧实例另测正常重启。

### E07 · P2 · 启动器中的鉴权检查和访问地址与实际行为不一致

- **位置**：`run_lan.bat:21`；`run_lan_3100.bat:20`；`mac-启动服务.sh:12`、`:26`、`:28`；`main.py:468`、`:750`。
- **证据**：多个启动器从 `core.providers` 导入 `get_configured_access_token`，但函数实际定义在 `main.py`；隔离环境确认 `hasattr(core.providers, 'get_configured_access_token') == False`。错误被重定向隐藏，导致总被解释为“没有配置凭证”。macOS shell 脚本打开局域网 IP，却没有传 `--host 0.0.0.0`，默认实际只监听 `127.0.0.1`。
- **影响**：即使设置了凭证仍出现错误提示；未覆盖 HOST 的默认 macOS shell 启动路径会打开不可访问的地址。这里是启动检测错误，不代表后端鉴权本身失效。
- **最小修改**：将无副作用的令牌读取函数放入已有公共配置模块并复用；本机启动打开回环地址，明确的局域网启动才传相应 host。浏览器 URL 从实际运行参数生成。
- **验收**：配置/未配置令牌各验证一次，提示与真实 API 401 行为一致；本机与 LAN 模式各测试所打印地址可访问，且监听范围符合选择。

### E08 · P2 · 普通启动会持续修改外部代理配置，缺乏明确开关

- **位置**：`main.py:724`、`:737`；`scripts/ensure_tailscale_bypass.py:25`、`:54`；`run.bat:15`。
- **证据**：应用生命周期总是启动每 60 秒执行一次的守护任务，发现控制接口后向其 `/configs` 发送 PATCH，把 `100.64.0.0/10` 加入 TUN 排除路由。使用替身 HTTP 响应已确认会产生该 PATCH；没有修改真实代理。
- **影响**：打开画布即改变本机另一应用的路由策略；用户手动调整后可能被守护任务再次覆盖，普通纯画布使用也承担该副作用。
- **最小修改**：改成网络设置中的明确可选操作或默认关闭的兼容开关，展示检测结果、变更和恢复方式；仅在用户选择启用后持续维护。复用现有网络设置模块即可。
- **验收**：默认启动时对控制接口零写请求；开启后仅修改目标项，关闭后不再恢复该规则；其他代理配置保持原值。

### E09 · P2 · 画布回收站与元数据之外的读改写操作仍有并发窗口

- **位置**：`routers/canvas.py:413`、`:489`、`:497`、`:504`；项目 CRUD 的 `:258`、`:296`；`save_projects()` 位于 `:230`。
- **证据级别**：源码确认；本次未把并发写入升级为已发生的数据损坏事件。
- **触发**：`api_touch_canvas()`、删除、恢复和永久删除先后调用各自的读取、修改和写入函数；这些操作没有像主画布 PUT 一样把“读取—判定—写入”包在同一个事务锁中。项目创建/更新同样是读取列表、修改内存对象、整体替换文件。单次 `load_canvas()` 或 `save_canvas()` 的文件操作虽受锁保护，但锁在两次调用之间释放。
- **影响**：两个页面同时触碰、删除/恢复或更新项目时，后完成的旧快照可能覆盖较新的字段；永久删除与保存交错时还可能出现删除后文件重新出现。主画布 PUT 已有乐观并发版本检查，这些相邻接口没有统一采用同一规则。
- **最小修改**：为 touch、回收站状态变更、永久删除和项目列表修改建立与主画布一致的锁内事务；对会覆盖用户内容的操作加入 `base_updated_at` 或明确的冲突响应。永久删除需在锁内协调缓存失效，并给保存请求定义明确的先后语义。
- **验收**：用屏障同时执行保存与 touch、保存与删除/恢复、项目更新与项目创建；结果满足明确的版本规则，缓存与磁盘一致，重启后不出现被覆盖或复活的记录。

## 4. 画布行为与访问边界复核

以下前端用例直接提取当前源码函数，以可控延迟响应和最小状态替身运行，不复制重写业务函数。它们证明状态机问题；本次未用完整浏览器重放所有 UI 步骤，后续应补充浏览器验收。

### F01 · P1 · 经典画布的延迟保存响应可以污染另一张画布

- **位置**：`static/js/canvas.js:1674`、`:1708`、`:2007`、`:2307`。
- **触发**：画布 A 发出保存请求后，在响应返回前通过画布列表打开 B；`openCanvas` 替换全局 `canvas`，但 A 的保存回调仍把响应合并到当前全局对象，没有核对发起请求时的画布 ID。
- **复现**：主审用实际 `saveCanvas` 函数延迟 A 的响应并切换到 B，完成后得到 `canvasId = A`，但当前 `nodeIds = [B-node]`。
- **影响**：后续保存可能把 B 的节点写到 A，或使界面与实际写入目标不一致，属于用户作品数据风险。
- **最小修改**：请求开始时捕获画布 ID、版本和加载代次，响应只更新所属画布；切换时明确处理待保存内容。保存中的队列也应按画布归属，不能使用同一组全局布尔量跨画布串接。
- **验收**：人为延迟 A 的 PUT，打开 B，再释放 A 的响应；B 的 ID、内容、版本保持不变；再次保存 B 只请求 B。补测返回列表、删除当前画布及快速连续打开。

### F02 · P1 · 撤销栈跨经典画布保留，会把上一张画布内容带入下一张

- **位置**：`static/js/canvas.js:502`、`:2307`、`:16158`、`:16167`。
- **触发**：在 A 上产生撤销记录，再在同一页面打开 B 后执行撤销。`openCanvas` 未清空或切换 undo/redo 栈，快照也没有画布身份校验。
- **复现**：使用实际 `captureUndoState`、`pushUndo`、`performUndo`，切换后撤销得到 `canvasId = B`、`nodeIds = [A-node]`；撤销随后调用 `scheduleSave()`。
- **影响**：上一张画布节点可被保存到当前画布；不仅是选中状态显示异常。
- **最小修改**：在确认切换画布时清空两个栈和待提交快照，或按画布 ID 分开维护。以清空为首选最小方案；同时为快照加入所属画布检查以阻止错用。
- **验收**：A 编辑后切 B，Ctrl+Z 不改变 B；切换后的 Ctrl+Y 也不恢复 A；单画布正常撤销/重做保持通过。

### F03 · P1 · 智能画布保存未串行化，且失败被静默吞掉

- **位置**：`static/js/smart-canvas.js:6112`、`:6116`、`:6127`、`:6164`。
- **触发**：第一次请求超过 450ms 时继续编辑，第二次定时保存仍会发出请求；函数设置 `canvasSyncInFlight`，却不以它阻止重入。任一请求结束都会把标志设回 false。网络异常和非 409 的失败响应没有用户反馈、明确脏状态或重试路径。
- **复现**：两次调用产生 2 个同时等待的请求；释放第一个响应时，第二个仍未完成，但 `canvasSyncInFlight` 已为 false。向第二个返回 500，函数正常结束，没有抛错或排入补存。
- **影响**：同一客户端产生额外版本冲突，远程同步可能在未完成保存时介入；断网、磁盘错误或鉴权失效时用户不知道内容未保存，关闭页面可能丢失操作。
- **最小修改**：一个在途请求加一个待保存标记，响应版本只向前推进；保留失败后的脏状态并显示可重试提示；恢复连接或用户重试后提交最新快照。复用经典画布已有串行化思路，但同时修复 F01 的画布归属问题。
- **验收**：慢网络下连续编辑只存在一个在途保存，最后状态最终落盘；401/413/500/断网均给出可见状态；重试不重复执行生成任务，成功后清除脏标记。

### F04 · P2 · 配置访问令牌后，原始素材 URL 仍然允许匿名读取

- **位置**：`main.py:477`、`:543`、`:643`、`:644`。
- **已复现行为**：在隔离副本设置虚构 `IC_ACCESS_TOKEN`，不提供凭证访问 `/api/canvases` 返回 401；访问两个新建的合成素材文件 `/output/audit-access-boundary.txt`、`/assets/audit-access-boundary.txt` 均返回 200，且为 `Cache-Control: public, max-age=86400`。
- **影响边界**：访问令牌当前保护 API，不是完整素材隐私边界。启用 LAN/远程访问时，获得已有素材地址的人仍可下载。**未证明可以枚举所有文件，也不将仅绑定回环的部署描述为公网暴露。**
- **最小修改**：明确素材是否应随令牌设为私有。若访问令牌用于保护整个工作空间，原始素材路径与派生预览应统一校验凭证，并设置合适的私有缓存策略；需要公开分享时使用独立的显式分享能力。
- **验收**：分别测试匿名、已认证和明确分享的原图/视频/缩略图请求；开启保护后匿名请求不得取回受保护字节，浏览器中的合法图片和视频加载仍正常。

### F05 · P2 · 画布节点主要依赖鼠标事件，键盘选择与操作路径不完整

- **位置**：`static/js/canvas.js:6533`、`:6542`；`static/js/smart-canvas.js:8502`；`static/index.html:871-880`。
- **证据级别**：源码确认的可访问性缺口；本次未宣称已完成读屏或真实键盘旅程验收。
- **证据**：经典画布节点由普通 `div.node` 承载，选择逻辑绑定 `onclick`，没有节点级 `tabindex`、可读名称或键盘选择/删除入口；智能画布的 `.image-node` 同样由鼠标按下事件驱动。外部工具 iframe 也没有统一的 `title` 属性。现有按钮和画布列表部分已有可访问属性，但不能覆盖节点操作本身。
- **影响**：仅使用键盘或辅助技术时，用户难以聚焦、选择、移动和删除节点；iframe 内容在辅助技术中缺少上下文名称。画布核心操作的可访问性无法由现有美学门禁保证。
- **最小修改**：为节点增加稳定的 `role`、`tabindex` 和本地化 `aria-label`，补充 Enter/Space 选择、Delete 删除及必要的快捷键提示；为每个 iframe 提供唯一且准确的 `title`。先定义焦点和画布平移的交互边界，再覆盖经典、智能和分组节点。
- **验收**：只用键盘完成聚焦、选择、删除、撤销和弹窗关闭；焦点可见且不被画布平移吞掉；读屏能区分节点类型和名称；工具 iframe 均有可识别标题，并在三种主题与窄视口下复核。

## 5. 架构、性能与体验优化建议

以下内容是有依据的工程建议，除明确注明外，不作为已复现功能故障。

### O01 · 按功能边界逐步拆分大文件，不做整体框架迁移

当前两个核心画布脚本合计 37,063 行；`routers/integrations.py` 为 4,158 行，`core/providers.py` 为 2,389 行。长度门禁允许它们继续留在历史预算内，不能解决修改影响范围过大的问题。

建议先围绕后续实际要修复的功能，提取保存与冲突处理、撤销/重做、媒体引用和任务状态等清晰边界。优先纯函数和少量明确的模块接口；保留现有原生 JS、iframe 视图及纯画布模式。不要为了“现代化”一次性迁移框架或建立插件工厂。

**验收**：每次只迁出一个职责，保留原行为；对应行为测试通过；记录主文件净减少量和调用关系，不用简单移动整段全局状态来冒充解耦。

### O02 · 建立大画布性能基线，再决定是否引入虚拟化

建议起始验收目标：在明确记录的参考设备上，1000 节点平移/缩放的主线程帧耗时 p95 不超过 16.7ms，文本输入无超过 100ms 的连续卡顿；若首次测量显示不适用，先记录真实基线再调整预算。**这些是目标，不是本次实测成绩。**

先定位全量 DOM 重建、连线重复计算、缩略图编码或大对象拷贝热点，再选择增量更新、帧内合并或视口裁剪；没有数据前不引入复杂索引系统。
